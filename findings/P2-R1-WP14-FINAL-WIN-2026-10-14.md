Additional limits visible in the reviewed method:

- `--disk` bypasses the target-open checks. ETW FileIo creates are unconditionally
  marked `write_open=False`; that is not evidence of read-only opening. The relevant
  [official FileIo_Create schema](https://learn.microsoft.com/en-us/windows/win32/etw/fileio-create)
  lists CreateOptions/FileAttributes/ShareAccess, not DesiredAccess. Narrow the
  claim to observed disk reads/no observed writes if justified, or add independently
  observable open-access evidence; never manufacture a mode flag.
- [DiskIo_TypeGroup1](https://learn.microsoft.com/en-us/windows/win32/etw/diskio-typegroup1)
  provides disk number,physical offset,transfer size and issuing thread, but no native
  API result/status. Completion plus exact verifyOK/0 is a proposed indirect result
  argument, not a captured ReadFile return. Preserve per-command software A6 exclusions;
  return a concrete limitation if exact native status cannot be observed.
- [ETW EventTrace_Header](https://learn.microsoft.com/en-us/windows/win32/etw/eventtrace-header)
  includes loss counters; consume/check them with a demonstrated zero-loss condition.
  Unknown/missing completeness is HELD rather than invented zero. PID/thread lifetime,
  executable/target/disk binding and precise full-sector successful range remain required.
- Software acknowledges that D scripts and real tracerpt output were not compiled/run
  on the named OSes. Synthetic XML cannot validate actual profile/export shape. First
  validate corrected collection off-card, retaining exact commands/versions/exit/errors.
- The recipe calls its62.5GB Windows image sparse without demonstrating sparse status.
  [Windows sparse-file documentation](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-files)
  makes sparse storage an explicit facility. Require verified sparseness/space safety,
  or use a smaller bounded >4GiB image rehearsal; do not assume ordinary file extension
